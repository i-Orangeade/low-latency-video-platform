# 2026-09-09 ZLMediaKit 并发压测

## 结论

自定义 ZLM 在本机短时测试中稳定承载 1、10、50、100 路 RTMP 输入。100 路阶段：

- 唯一在线流数始终为 100；
- 容器 CPU 平均值为 198.90%，P95 为 217.34%；
- 容器 RSS 平均值为 272.39 MiB，P95 为 276.56 MiB；
- 输入吞吐约 167.62 Mbps；
- 抽样流为 25 FPS、约 1.70 Mbps，时间戳回退次数为 0。

机器为 8 逻辑核 Linux 主机。Docker CPU 的 100% 约等于一个逻辑核，因此 100 路阶段平均使用约两个逻辑核。

可提交的原始汇总见 [2026-09-09-summary.json](2026-09-09-summary.json)。完整逐样本输出默认位于 `benchmark-results/20260909-final-matrix-v2/`，该目录不提交 Git。

## 复现

```bash
COUNTS='1 10 50 100' \
DURATION=25 \
WARMUP=12 \
SAMPLE_INTERVAL=1 \
RAMP_MS=100 \
STARTUP_TIMEOUT=60 \
DRONE_STREAM_ZLM_SECRET='<local-api-secret>' \
scripts/run_benchmark_matrix.sh
```

压测器先生成一份 1280×720、25 FPS、约 1.5 Mbps 的 H.264 FLV 样本。每个 FFmpeg 发布进程循环读取该样本并使用 `-c:v copy` 推流，避免把宿主机并行编码能力混入 ZLM 转发测试。发布者按 100 ms 间隔接入。

脚本不再以固定休眠判断预热完成，而是轮询 ZLM media list，按唯一 `stream` 字段去重；达到目标流数后才开始采样。资源数据直接来自 Docker Engine Unix Socket stats API。

## 调试发现

一次性并发启动 100 个发布者会形成 Hook 连接风暴，部分 `on_publish` 请求收到 EOF。100 ms 梯度接入后 100 路全部通过鉴权。这个结果说明当前同步 Hook 控制面存在突发接入边界，不应表述为“任意 100 路瞬时接入”。

早期配置使用了固定 ZLM commit 不支持的 `hook.admin_params`，导致 Hook 密钥没有进入请求。现改为 Hook URL 查询 token，并由后端使用常量时间比较。

多协议 `on_stream_changed` 会为同一输入产生重复状态写入。当前状态同步只订阅源 `rtmp` schema；SQLite 启用 WAL、30 秒 busy timeout，并扩大连接池。生产环境仍应迁移到 PostgreSQL、消息队列或异步批量写入。

故障注入还发现单次 Hook 重试不足以覆盖 FastAPI 容器恢复窗口。当前配置调整为最多
5 次、间隔 1 秒，并由 `scripts/failure_recovery_test.sh` 验证控制面短暂中断后
发布鉴权可恢复。

## 限制

- 每档只有 7 个稳态资源样本，适合项目验收，不代表小时级稳定性结论。
- 当前只测 RTMP 输入和 ZLM 内部协议派生，没有为每路建立真实播放端。
- 当前结果验证的是自定义版本容量；严格的“原版与修改版性能回归”仍需在同一机器、同一 commit、相同容器生命周期下做 A/B。
- RSS 包含 ZLM WebRTC/ICE 初始化及前序实验留下的进程内缓存，不应解读为每路独占内存。
