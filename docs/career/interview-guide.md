# 高频面试问题与回答框架

> 回答结构统一采用：结论 → 项目事实 → 原理 → 风险/验证。明确区分“当前实现”“合理设计”“待验证”，不要把 ZLMediaKit 内部机制说成自己的实现。

## 1. 项目的线程模型是什么？

短答：

“我自己的业务层没有实现媒体线程池。当前媒体收发与协议转换由 ZLMediaKit 负责；FastAPI 是控制面，前端直接拉 ZLM。基础实验中实现了单线程 epoll echo server 和多生产者/多消费者有界队列；延迟探针用 fork/exec 启动 ffprobe 并以 poll 读取管道。若讨论 ZLM 内部线程模型，我会先固定源码版本并用运行证据验证，当前不能声称完成了源码级分析。”

展开框架：

1. 媒体路径：FFmpeg/C++ 进程 → ZLM → 浏览器，不经过 FastAPI。
2. 控制路径：FastAPI 请求 ZLM HTTP API；数据库 CRUD 为同步 SQLAlchemy。
3. 前端：浏览器事件循环管理 UI，WebRTC 通过 `RTCPeerConnection` 回调驱动；`mpegts.js` 的内部实现不应无证据归因于项目代码。
4. 设计时要明确连接归属线程、回调在哪个线程触发、跨线程对象由谁持有、退出顺序如何保证。
5. 验证方法：日志记录 thread id、断点观察回调、TSAN、压测时看线程数/上下文切换、关闭时做长稳与异常退出。

常见追问：“为什么不能每路流一个线程？”  
答题点：线程栈与调度成本随流数增长；媒体连接更适合事件驱动 I/O，CPU 密集编码则应与 I/O 线程隔离。是否采用每线程事件循环，要以 ZLM 版本源码为准。

## 2. RingBuffer 在直播系统中解决什么问题？

短答：

“RingBuffer 适合保存有界的最近数据，让新读者从关键帧附近快速加入，并隔离生产者与多个消费者。核心不是容器名字，而是覆盖策略、GOP 边界、慢消费者、线程归属和对象生命周期。”

展开框架：

- 写入端通常追加帧或 RTP 包；读者维护自己的读取位置。
- 容量有界可防止无上限内存增长，但覆盖未读数据时必须定义丢弃或断开策略。
- 视频不能随意从 P/B 帧开始，常需缓存 SPS/PPS 与最近 GOP，从 I 帧建立可解码起点。
- 慢消费者若阻塞写线程，会拖累所有观看者；更常见做法是丢旧数据、跳到最新关键帧或关闭连接。
- 单生产者/单消费者、单生产者/多消费者的同步策略不同；无锁不等于无等待，也不必然更快。
- 指标：队列深度、覆盖次数、读者滞后、每路缓存字节、关键帧等待、丢帧数。

项目边界：

当前仓库没有 RingBuffer 实现，但 `labs/src/bounded_queue_demo.cpp` 有 mutex + condition_variable 的有界 MPMC 阻塞队列，并有测试与 TSAN 构建选项。它能证明并发基础，不等同于支持 GOP/多读者游标的媒体 RingBuffer；更不能把 ZLM 自身 RingBuffer 说成自研。

## 3. 如何设计一个有界队列？

回答框架：

1. 先定语义：容量按元素还是字节；满时阻塞、丢最新、丢最旧还是断开。
2. 明确并发模型：SPSC 可用原子 head/tail；MPMC 通常先用 mutex + condition_variable 建立正确基线。
3. 正确处理虚假唤醒，以谓词等待；关闭时唤醒生产者和消费者。
4. 明确移动语义、异常安全和析构顺序，避免线程仍访问已销毁队列。
5. 用单测覆盖空/满/关闭/超时，用 TSAN 查竞争，用压力测试比较吞吐和尾延迟。

联系本项目：采集帧进入发送线程时可用有界队列提供背压；实时场景通常宁可丢过期帧，也不能无限累积并把延迟越堆越高。具体丢帧策略仍需结合关键帧。

## 4. 为什么时间戳是低延迟测量的难点？

短答：

“测量值只有在事件定义、时钟域和样本配对都明确时才可信。当前工具把 FFmpeg 启动前的同机 realtime 锚点与从零开始的 PTS 关联，再由 ffprobe 读取真实播放 URL；它测的是源播放时间线到帧记录到达探针，不是玻璃到玻璃。”

回答框架：

- 先定义起终点：采集完成、送入编码器、网络发送、解码完成或画面呈现，结果含义不同。
- 探针当前为了关联 sidecar 和帧 PTS 使用同机 `CLOCK_REALTIME`；超时控制使用单调时钟。realtime 可能被校时调整，因此长实验需观察时钟跳变。
- 跨机单向延迟需要 PTP/NTP 校时并记录偏差，或者采用往返测量；仅相减两台机器 wall clock 会把时钟误差算入网络延迟。
- 需要把帧 ID/时间码带过编码与传输链路，可用画面烧录、SEI、自定义元数据或可识别图案；方案要验证不会被转封装丢失。
- PTS/DTS 是媒体时间线，不等于真实墙钟；有 B 帧时解码序和显示序不同。当前 FFmpeg 参数关闭 B 帧，能简化但不能消除全部缓冲。
- 报告 P50/P95/P99、首帧时间和样本数；平均值无法描述抖动。

项目事实：ZLM 活跃配置 `modify_stamp=2` 会按源流相对增量并校正跳变/回退。它是协议转换策略，不是端到端测量本身，影响需做 A/B 实验。

## 5. WebRTC 为什么通常比 HTTP-FLV 更低延迟？

回答框架：

- HTTP-FLV 通常基于 TCP，可靠有序传输遇到丢包会产生队头阻塞；播放器还可能维持缓冲。
- WebRTC 面向实时交互，常用 UDP，结合 SRTP、RTCP、NACK、拥塞控制和抖动缓冲，在完整性与时效性之间动态权衡。
- WebRTC 并非必然更低延迟：若 ICE 失败转 TCP/TURN、编码或播放缓冲过大、关键帧等待、网络严重抖动，优势会缩小。
- 公平对比必须固定编码输入、GOP、码率、网络条件和统计口径。

项目事实：

- 后端可生成 `/index/api/webrtc?...type=play` 地址。
- 前端已创建 recvonly audio/video transceiver，等待 ICE gathering，POST offer SDP 并设置 answer SDP。
- ZLM 配置启用 WebRTC 转换并含 ICE/TURN/RTC 相关参数。
- Docker Compose 已映射 RTC 8001 TCP/UDP（避免与 FastAPI 8000 冲突），并通过环境变量设置外部 candidate IP；公网 NAT/TURN 路径仍需在目标环境抓包验证。
- `PerformanceTest.vue` 中 280 ms WebRTC 数据由按钮写入，是示例数据，不是基准测试。

## 6. WebRTC 建链过程如何讲？

框架：

1. 信令交换 SDP offer/answer，协商 codec、媒体方向和传输参数。
2. ICE 收集 host/server-reflexive/relay candidate，并做连通性检查。
3. 选定 candidate pair 后完成 DTLS 握手，导出 SRTP 密钥。
4. 媒体通过 SRTP 传输，RTCP 提供质量反馈，NACK/PLI 等协助恢复。
5. NAT 后部署要考虑公网可见 IP、UDP 端口映射和 TURN；不能只看“接口返回 200”就认为媒体已打通。

项目回答要加一句：“以上是协议原理；本项目已实现信令和端口配置，但公网浏览器建链仍以 ICE candidate 与抓包证据为准。”

## 7. Hook 为什么必须幂等？

短答：

“ZLM 配置了失败重试，网络超时也可能出现服务端已写库但客户端未收到响应的情况，所以同一事件可能重复到达。当前录像以 `file_path` 唯一约束并处理并发唯一冲突；离线告警只做‘同流未读告警’的先查后写，串行重复可去重，并发下仍可能重复。”

设计框架：

- 事件身份：优先使用上游事件 ID；没有时用 `mediaServerId + hook 类型 + app + stream + 关键时间/文件路径` 构造稳定键。
- 数据库兜底：对事件键或录像唯一组合建唯一索引，使用 upsert/捕获唯一冲突。
- 事务边界：业务写入与幂等记录同一事务提交。
- 并发重复：不能只做“先查再写”，两个请求可能同时通过查询。
- 返回策略：重复事件也返回成功，避免上游继续重试。
- 安全：校验 secret/签名、限制来源和请求体；幂等与鉴权是两件事。
- 可观测：记录首次/重复、处理耗时、失败类型和重试次数，但避免记录真实 secret。

当前实现与风险：

- 所有 Hook 都用 `hmac.compare_digest` 校验 Hook URL 的独立 token；payload secret/`admin_params` 只作为兼容输入。
- `on_publish` 在活跃配置中已启用，会拒绝未知或禁用的流；独立 Hook token 通过 URL 查询参数传递。
- `on_stream_changed` 只订阅源 RTMP schema，更新设备在线状态、恢复时解决未读离线告警，离线时做应用层去重；缺少并发唯一约束。
- `on_record_mp4` 对 `file_path` 有数据库唯一约束并捕获 `IntegrityError`，重复请求返回成功。

## 8. 如何测试 Hook 幂等？

回答框架：

1. 同一 payload 串行发送 N 次，断言只有一条业务记录。
2. 并发发送同一 payload，验证唯一约束而非进程内锁发挥作用。
3. 模拟“提交成功后响应丢失”，重试仍返回成功。
4. 相同流但不同真实事件不应误去重。
5. 错误 secret、缺字段和超大请求体应拒绝且不落库。
6. 多进程/多实例下重复测试，证明方案不依赖单实例内存。

## 9. 如何做压测，为什么不能只报 QPS？

短答：

“这个项目至少有三类负载：控制面短请求、播放长连接、媒体收发。它们的瓶颈和指标不同，必须分开测。”

压测矩阵：

- FastAPI 控制面：健康检查、状态查询、CRUD；看吞吐、P50/P95/P99、错误率、数据库锁等待、ZLM API 上游耗时。
- Hook：突发回调与重复事件；看幂等冲突、写入延迟和失败重试。
- HTTP-FLV：并发长连接；看首帧时间、稳定连接数、出口带宽、ZLM CPU/内存、断连率。
- WebRTC：并发会话、ICE 成功率、UDP/TCP/TURN 路径、丢包、RTT、jitter、NACK 和码率。
- 推流：并发流数、每流码率/FPS、转协议开关、GOP 缓存和资源增长。
- 长稳：数小时运行，看 RSS 趋势、文件描述符、线程、数据库增长和恢复时间。

实验纪律：

1. 固定硬件、版本、编码参数和网络拓扑。
2. 预热后采样，重复多轮并报告样本数。
3. 负载发生器与被测服务尽量分机，避免争抢 CPU/网卡。
4. 先找饱和点，再用 profiling、系统指标和应用日志归因。
5. 不预填结果；`[并发/吞吐/延迟]` 只有实测后才能进简历。

当前项目已完成 1/10/50/100 路短时稳态矩阵。100 路采用预编码 H.264 codec copy 和 100 ms 梯度接入，8 逻辑核主机上 ZLM CPU 平均 198.90%、P95 217.34%、RSS P95 276.56 MiB，抽样流保持 25 FPS 且 DTS 回退为 0。每档只有 7 个资源样本，且没有建立 100 个播放端，因此只能称为短时输入容量结果。

## 10. 弱网脚本的 HTB、TBF、netem 各做什么？

- HTB：建立根层级和类别，承载后续流量整形。
- TBF：令牌桶限速，并通过 burst/latency 定义突发和排队边界。
- netem：注入时延和丢包。
- 当前层级为 HTB root → TBF → netem，脚本支持 dry-run 与规则存在性校验。
- 风险：默认设备是 `lo`，会影响该接口上的其他本地流量；应用后必须 clear。单向施加在哪个接口会决定影响的是入站还是出站，实验报告必须写清拓扑。

## 11. 为什么选择 `veryfast + zerolatency + GOP 50 + bf 0`？

回答框架：

- `veryfast` 降低编码计算压力，但通常以压缩效率为代价。
- `zerolatency` 减少面向离线压缩的缓冲。
- 25 fps 下 GOP 50 约为 2 秒关键帧间隔；新观众可能等待关键帧，需在码率、压缩率和首屏之间权衡。
- 禁用 B 帧减少重排序等待，也会影响压缩效率。
- 当前参数只是测试基线，尚未通过矩阵实验得出“最优”结论。

## 12. 为什么 FastAPI 没有代理视频？

答：

“FastAPI 只返回地址、状态和控制结果，浏览器直接连接 ZLM。这样减少数据复制与一次网络跳转，让擅长媒体协议、长连接和转封装的 ZLM 承担媒体面，让业务后端聚焦设备、告警、录像与实验数据。代价是前端必须能访问 ZLM，并正确处理跨域、鉴权和公网地址。”

## 13. 当前项目最大的技术债是什么？

建议答法：

1. 延迟探针计算和上传链路已完成，但严格玻璃到玻璃数字仍缺少外部画面时钟和跨机校时。
2. WebRTC 前端建链代码已存在，但端口/NAT 和真实浏览器链路尚未闭环。
3. Hook 已有密钥校验、发布白名单和基础去重，但离线告警仍缺并发唯一约束，瞬时连接风暴需要队列或限流。
4. 已有启动、推流、QoS、断流告警和服务重启自动化；仍缺真实浏览器播放与录像文件生成的端到端自动化。
5. C++ 工具以 `std::system` 调外部命令为主，缺少进程控制、错误分类和输入转义边界。

收尾：“我会先补证据链，再优化；因为没有正确、可重复的测量，性能优化没有可信基线。”
